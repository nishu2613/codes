This script downloads protein sequences from UniProt and combines them into one FASTA file.

File: [fasta_extract_from_uni.py](/home/neelamnishanth/Kp_data_processing/codes_for_preprocessing/fasta_extract_from_uni.py)

### What it does

1. **Asks for two paths**
   - A text file containing UniProt IDs.
   - The output FASTA file path.

2. **Validates the input file**
   - Exits if the input file does not exist.

3. **Reads UniProt IDs**
   - Ignores blank lines.
   - Ignores lines beginning with `#`.
   - Removes duplicate IDs while preserving their order.

4. **Downloads each sequence**
   - Requests sequences from:

   ```text
   https://rest.uniprot.org/uniprotkb/{ID}.fasta
   ```

5. **Retries temporary failures**
   - Attempts each download up to 3 times.
   - Retries network errors, HTTP `429`, and server errors (`500–599`).
   - Uses increasing delays between retries.
   - Respects the server’s `Retry-After` header when available.

6. **Writes successful results**
   - Appends all downloaded FASTA records to the requested output file.

7. **Records failures**
   - Failed UniProt IDs are written to:

   ```text
   <output-folder>/failed_uniprot_ids.txt
   ```

8. **Waits between requests**
   - Pauses for `0.2` seconds after each ID to reduce server load.

### Example input

```text
P69905
P68871
# This is a comment
P69905
```

The duplicate `P69905` is downloaded only once.

### Example usage

Run:

```bash
python fasta_extract_from_uni.py
```

Then enter:

```text
Path to UniProt IDs txt file: ids.txt
Output FASTA path to write combined sequences: results/proteins.fasta
```

The script creates:

```text
results/proteins.fasta
results/failed_uniprot_ids.txt
```

The output FASTA file contains all successfully retrieved protein sequences.

|---|---|---|

| UniProt lookup | Direct UniProtKB URL only | Three fallback methods |
| Handles secondary/merged IDs | No | Yes, using `sec_acc` |
| Handles UniParc IDs | No | Yes |
| Multiple returned FASTA records | Writes all returned text | Extracts only the first FASTA record |
| FASTA headers | Keeps UniProt’s original header | Adds queried ID to the header |
| Retry behavior | Retries the direct URL | Retries each fallback endpoint |
| Failure message | “Failed after retries” | “Failed across all tiers” |

### Important behavior in `fetch_fasta.py`

For every ID, it tries these sources in order:

1. **Direct UniProtKB entry**

   ```text
   /uniprotkb/{uid}.fasta
   ```

2. **Secondary accession lookup**

   ```text
   /uniprotkb/stream?query=sec_acc:{uid}
   ```

   If a taxonomy ID is entered, it also adds:

   ```text
   AND taxonomy_id:{tax_id}
   ```

3. **UniParc archive**

   ```text
   /uniparc/stream?query={uid}&format=fasta
   ```

This means `fetch_fasta.py` can retrieve sequences when an ID is old, merged, secondary, or available through UniParc, while the older script would mark it as failed.

### FASTA header difference

The older script may write a header like:

```text
>sp|P69905|HBA_HUMAN Hemoglobin subunit alpha
```

The newer script changes it to something like:

```text
>P69905 | sp|P69905|HBA_HUMAN Hemoglobin subunit alpha
```

This makes the originally queried ID easy to identify.

### Summary

Use `fasta_extract_from_uni.py` when you only need direct UniProtKB lookups.

Use `fetch_fasta.py` when you need:

- Better recovery for missing or obsolete IDs
- Secondary accession support
- UniParc fallback
- Taxonomy filtering
- One FASTA record per input ID
- Standardized headers with the queried ID included


### FASTA input

The FASTA header must follow a format similar to:

```text
>1IWP_3|Chains A [auth A], B [auth C]|Some protein description
```

The script extracts:

- `1IWP` → PDB ID
- `3` → entity ID
- `A,B` → label chain IDs
- `A,C` → author/auth chain IDs
- `Some protein description` → description

The sequence lines themselves are not processed. Only header lines beginning with `>` are used.

### mmCIF input

The mmCIF file must correspond to the PDB ID from the FASTA header.

For example:

```text
FASTA header: >1IWP_3|Chains A|Protein
mmCIF file:   1IWP.cif
```

The script reads the mmCIF `_entity_poly` category and finds the matching entity ID. It extracts:

- Whether the entity is a polypeptide
- Whether it contains non-standard monomers

## Output

The output filename is fixed:

```text
entity_chain_summary.csv
```

It is created in the directory where the script is run.

The CSV contains these columns:

| Column | Meaning |
|---|---|
| `pdb_id` | PDB structure ID from the FASTA header |
| `entity_id` | Entity number from the FASTA header |
| `label_ids` | mmCIF/label chain IDs from the FASTA header |
| `auth_ids` | Author-assigned chain IDs |
| `nstd_monomer` | Whether non-standard monomers are present |
| `is_polypeptide` | Whether mmCIF identifies the entity as a polypeptide |
| `is_biological` | Whether it is considered biological by this script |
| `description` | Protein description from the FASTA header |

## How `is_biological` is calculated

The script sets:

```python
is_biological = is_polypeptide and not inhibitory_flag
```

So an entry is marked `True` only when:

1. The mmCIF entity is a polypeptide, and
2. The FASTA description does not contain:
   - `inhibitory protein`
   - `inhibitory protien`

Otherwise, it is marked `False`.

## Example output

For a matching FASTA and mmCIF entry, the CSV may contain:

```csv
pdb_id,entity_id,label_ids,auth_ids,nstd_monomer,is_polypeptide,is_biological,description
1IWP,3,A,A,no,True,True,Some protein description
```

## In simple terms

The script answers:

> For each protein entity listed in the FASTA headers, which PDB structure and chains does it belong to, is it a polypeptide, does it contain non-standard monomers, and should it be considered biological?

It skips malformed FASTA headers and FASTA entries for which a matching mmCIF file cannot be found.

## What it extracts from each CIF file

The script reads the mmCIF category:

```text
_struct_ref.
```

Specifically, it extracts:

- `db_name`
- `pdbx_db_accession`
- `entity_id`

It keeps only rows where:


```json
  "entity_id": "3"
```


## How clustering works

Files are placed in the same cluster only when they have the exact same set of UniProt accessions.

Example:

```text
1ABC.cif → P12345, Q67890
2XYZ.cif → Q67890, P12345
3AAA.cif → P12345
```

The result is:

```text
Cluster 1:
  1ABC.cif
  2XYZ.cif

Cluster 2:
  3AAA.cif
```

The order of accessions does not matter because the script sorts them before comparing.

This is **not sequence clustering** and does not compare protein sequence similarity. It only compares the UniProt accession sets associated with each CIF file.

Example:

```csv

```

## Overall purpose

The script answers:

> Which CIF structures are associated with the same UniProt protein or combination of proteins?

It is useful for grouping structural files based on their UniProt annotations while optionally restricting the analysis to selected PDB IDs and biological entities.

3. **Optional output CSV**


## Processing steps

### 1. Keeps only biological entities

Rows where:

```text
is_biological = True
```

are processed.

Rows marked `False` are skipped.

### 2. Finds the mmCIF file

For each row, it uses the `pdb_id` to locate the corresponding CIF file.

For example:

```text
pdb_id = 1ABC
```

It searches for:

```text

1abc.cif
1ABC.cif.gz
```

### 3. Uses the label chain IDs

It reads the `label_ids` column.

Example:

```text
label_ids = A,B
```

It processes chains `A` and `B` separately.

The script uses `label_ids`, not `auth_ids`.

### 4. Confirms chain and entity in the mmCIF

It reads the `_atom_site` table and searches for rows where both match:

```text
_atom_site.label_entity_id == entity_id
_atom_site.label_asym_id == chain_id
```

For example:

```text
entity_id = 3
chain_id = A
```

It looks for atoms belonging to entity `3` and label chain `A`.

This is where the chain and entity information is actually validated against the mmCIF file.

### `start_position`

The smallest observed residue number.

### `end_position`

The largest observed residue number.

### `non_standard_residues`

Non-standard residues found as `HETATM`, excluding water `HOH`.

Example:

```text
MSE:10;SEP:45
```

This is `True` when all integer residue positions between the first and last observed positions are present.


```text
False
```

### `has_insertion_code`

This is `True` if the mmCIF contains insertion codes such as:

```text
10A
10B
```

It records:

- Missing CIF files
- Chains with no matching atoms

The script does **not** extract the amino-acid sequence itself. It extracts structural residue-position information and checks whether atoms exist for the requested entity and label chain.

## What the script does

For each mutation CSV:

### 1. Reads the mutation data

```python
df = pd.read_csv(input_csv)
```

### 2. Keeps only substitutions

```python
subs_df = df[df['Mutation Type'] == 'Substitution'].copy()
```

It ignores:

- Deletions
- Insertions

Only amino-acid replacements are used.

### 3. Calculates the total substitution count at each position

```python
position_totals = subs_df.groupby(
    'Aligned Position'
)['Count'].transform('sum')
```

For example:

```text
Position 25:
A → V: Count = 8
A → T: Count = 2
```

Total substitutions at position 25:

```text
8 + 2 = 10
```

### 4. Calculates the PSS value

```python
subs_df['PSS'] = subs_df['Count'] / position_totals * 100
```

For the example:

```text
A → V = 8 / 10 × 100 = 80%
A → T = 2 / 10 × 100 = 20%
```

## Output

The output filename is created by replacing:

```text
_mutations.csv
```

with:

```text
_PSSM.csv
```

Example:

```text

Output:

```

The output contains the original substitution rows plus a new column:

```text

```

Example:

```csv
Aligned Position,Reference Residue,Mutation Type,Mutated Residue,Count,PSS
25,A,Substitution,V,8,80.0
25,A,Substitution,T,2,20.0
```

## Meaning of the PSS value

The `PSS` value represents the percentage distribution of observed substitutions at a particular aligned position.

| PSS value | Meaning |
|---:|---|
| 100% | All substitutions at that position are the same amino acid |
| 80% | That substitution is dominant among substitutions at the position |
| 50% | Half of the observed substitutions are that amino acid |
| Low value | The substitution is less common at that position |

For every aligned position, the PSS values for all substitution types will normally sum to approximately:

```text
100%
```

## Important limitation

This script does not calculate a classical statistical PSSM based on log-odds scores.

It calculates:

```text
percentage of each substitution among all substitutions at that position
```

For example, if there are 100 homologs and only 10 contain substitutions at position 25:

```text
8 sequences: A → V
2 sequences: A → T
90 sequences: A → A
```

The script calculates:

```text
A → V = 80%
A → T = 20%
```

It does not include the 90 unchanged sequences in the denominator.

Therefore, the score means:

> Among the observed substitutions at this position, how frequently does each mutated residue occur?

It does not mean:

> What percentage of all homologs contain this mutation?

The generated PSSM files can then be used to identify positions where substitutions are concentrated or where particular amino-acid changes are common among the homologs.
